# Chatbot 2.0 — message ordering, database write access, and the autonomy ceiling

**Date:** 2026-08-16 · **Status:** approved, moving to implementation plan

## Problem

Two defects, one feature area.

1. **Chat history renders out of order.** Reopening or refreshing a conversation shows every user message grouped together, followed by every assistant message. The turn structure is destroyed.
2. **The chatbot reports it has read-only database access.** Asked to create a job and place it in a board column, it answers that it can read the workspace but cannot write to it, and offers to format text for the user to paste manually.

Both are fixed here, together with the scaffolding for the longer-term goal: the chat becomes the primary surface for operating atTrack, with an agent that can carry out multi-step work autonomously.

## Part 1 — Message ordering

### Root cause

Assistant messages are created client-side without a timestamp. [lib/ai-chatbot/use-chat.ts:78](../../../lib/ai-chatbot/use-chat.ts):

```ts
{ id: assistantId, role: "assistant", content: "" }
```

The persistence layer fills the gap at save time. [lib/ai-chatbot/persistence.ts:49](../../../lib/ai-chatbot/persistence.ts):

```ts
created_at: m.createdAt ?? new Date().toISOString()
```

`upsertSessionToDb` rewrites every message row on every save, so each assistant row is re-stamped with the *current save time* on every subsequent turn. After four turns the user messages hold their real send times `t1 < t2 < t3 < t4` while every assistant message holds the most recent save time `T > t4`.

The read path sorts on that column. [lib/ai-chatbot/persistence.ts:92](../../../lib/ai-chatbot/persistence.ts):

```ts
.sort((a, b) => (a.createdAt ?? "").localeCompare(b.createdAt ?? ""))
```

All user messages therefore sort ahead of all assistant messages. This is timestamp corruption, not a sorting bug.

A timestamp-only fix is insufficient: the user and assistant message objects are both constructed in the same synchronous tick of `runStream`, so `new Date().toISOString()` returns an identical millisecond for both. That leaves a tie with no tiebreaker, and the row order returned by the unordered `chat_messages` select decides the outcome.

### Fix

Order by position, not by clock.

- Add `seq INTEGER` to `chat_messages` — `lib/db/schema.sql` for new databases, `COLUMN_MIGRATIONS` in `lib/db/sqlite.ts` for existing ones, per the repository's schema-change convention.
- `upsertSessionToDb` already receives `input.messages` as an ordered array. Write `seq` from the loop index. No clock is involved and no tie is possible.
- `loadSessionsFromDb` selects `seq` and sorts on it ascending, falling back to `created_at` for rows written before the migration and never re-saved.
- Backfill existing history by deriving `seq` from SQLite's implicit `rowid`. Messages were first inserted in array order, so `rowid` preserves the original turn order even though `created_at` no longer does.
- Set `createdAt` on the assistant message where it is constructed, so displayed timestamps are honest. This does not affect ordering, which now depends only on `seq`.

Any session that is opened and continued rewrites its own `seq` values correctly, so the fix is self-healing beyond the one-time backfill.

Both requested behaviours follow from preserving literal position: strict `user → assistant` alternation, and consecutive user messages when the user sends several before a reply.

## Part 2 — Database write access (Tier 1)

### Root cause

The write and delete tools are fully implemented and correctly registered. [lib/ai/tools/write-database.ts](../../../lib/ai/tools/write-database.ts) and [lib/ai/tools/delete-database.ts](../../../lib/ai/tools/delete-database.ts) are both present in `TOOL_REGISTRY` ([lib/ai/tools/registry.ts:21](../../../lib/ai/tools/registry.ts)) and both listed on the `general` agent ([lib/ai/agents/registry.ts:34](../../../lib/ai/agents/registry.ts)). The design they implement is [2026-08-15-chatbot-db-write-delete-design.md](2026-08-15-chatbot-db-write-delete-design.md).

Only the permission gate is shut. [lib/ai-chatbot/workspace.ts:180](../../../lib/ai-chatbot/workspace.ts) seeds the `db_query` source as `enabled: false`. That flag propagates:

`deriveWorkspaceSources` seed → `defaultEnabledIds` ([app/(dashboard)/ai-builder/chatbot/page.tsx:223](<../../../app/(dashboard)/ai-builder/chatbot/page.tsx>)) → the session's `connectedSourceIds` → the request body's `enabledSources` → `resolvedEnabled` ([app/api/chat/route.ts:56](../../../app/api/chat/route.ts)) → `isSourceAllowed` ([lib/ai/tools/registry.ts:40](../../../lib/ai/tools/registry.ts)).

With the source off, every tool carrying `sourceId: "db_query"` is filtered out of the declarations sent to the model. All three database tools disappear together. The model is not refusing — it has no write tool to call, and says so accurately.

The reads it does have come from the separately-seeded `search_jobs`, `search_contacts`, and related tools, which are `enabled: true`. That asymmetry is exactly what produces "I can read your workspace but cannot add to it".

Two further causes compound it, and unblocking the source alone does not fix the reported behaviour.

**The system prompt names a read-only path as the way to use the database.** [lib/ai-chatbot/prompt.ts:59](../../../lib/ai-chatbot/prompt.ts) instructs the model to answer database requests by emitting a ` ```sql SELECT... ``` ` block and asking the user to click "Approve & Execute Query". This is a real second path: `components/ai-chatbot/markdown.tsx` renders any SQL block with an approve button wired to `executeLocalSqlQuery` ([lib/actions/database-query.ts](../../../lib/actions/database-query.ts)), which regex-blocks `INSERT`, `UPDATE`, `DELETE` and every other mutating statement. It cannot write under any circumstances. So the model's report that it "can only execute read-only queries" was accurate about the path its own prompt directed it to, and the manual approval click the user objects to is that path working as designed. The prompt must direct the model to the tools instead, reserving the SQL block for complex multi-table reads the tools cannot express.

**The read tool's description forbids writing.** [lib/ai/tools/query-database.ts:30](../../../lib/ai/tools/query-database.ts) still ends with "Never ask for or expect write/delete access", written before `write_database` existed. It now contradicts the write tool sitting beside it in the same registry.

A downstream symptom of having no write tool: the model fabricated `SET stage = 'MCQ/Screening'`. There is no `stage` column — board placement is `list_id` and `status` is derived from it. Routing through `write_database`'s `list` field removes the guesswork, and the revised prompt states the rule explicitly.

### Fix

1. **Seed `db_query` as `enabled: true`.** It requires no credentials (`auth: { status: "none" }`) and addresses the user's own local database. This is unlike `obsidian` and `github`, which stay `false` because they need a vault path and a personal access token respectively.

2. **Backfill `db_query` into existing sessions once.** Existing sessions carry a frozen `connectedSourceIds` array in SQLite that predates the flip and does not contain `db_query`; the load path prefers that stored array whenever it is non-empty ([app/(dashboard)/ai-builder/chatbot/page.tsx:270](<../../../app/(dashboard)/ai-builder/chatbot/page.tsx>)). Without this step the seed change would only reach newly created chats.

   The backfill must be **one-time**, not a union applied on every load. Source toggles on this page are per-session: `handleToggleSource` ([app/(dashboard)/ai-builder/chatbot/page.tsx:519](<../../../app/(dashboard)/ai-builder/chatbot/page.tsx>)) writes only to the session's `connectedSourceIds` and never touches the global override store. A union re-applied on every load would therefore silently undo a user who switched database access off in a given chat, resurrecting it on the next reload. Gate the backfill behind a persisted one-shot marker in `localStorage`; once it has run, per-session toggles are authoritative forever.

3. **Explicit user toggles continue to win.** After the one-shot backfill, turning the source off in a chat stays off in that chat. The global override store (`isSourceEnabled`, [lib/ai-chatbot/source-permissions.ts:68](../../../lib/ai-chatbot/source-permissions.ts)) continues to govern the seed default independently and is not bypassed.

4. **Emit audit lines from the write and delete tools.** Neither currently records anything. Reuse the existing trail, `logResourceActivity` in [lib/actions/activity-log.ts](../../../lib/actions/activity-log.ts) — an NDJSON log under `.data/logs`, no table required. Its established rule that field values never appear in the log applies unchanged: record the action, the table, and the row id, never the contents.

Delete behaviour is unchanged. The two-turn confirmation gate built in the previous design stays exactly as it is: a delete is proposed with the affected rows and the literal SQL, and only executes when the user confirms in a later turn.

### Permission model

The client resolves permissions and sends them in the request body; the server trusts that array. This is consistent with the existing local single-user trust boundary described in `docs/SECURITY.md` and is not changed here. The durable guardrails live server-side in the tools themselves, and hold regardless of what the client sends:

- The owner column is forced to `ctx.userId` and never read from model-supplied values, so cross-user writes are impossible.
- Per-table column allowlists bound what the model can set, with `id`, `user_id`, `status`, `created_at`, and `updated_at` blocked on every table.
- `jobs.status` remains derived from `list_id`, and placing a job in an Applied-kind column routes through the existing `ensureApplication` helper rather than writing the column directly, preserving the invariant in `CLAUDE.md`.

## Part 3 — The autonomy ceiling (Tier 2 and Tier 3)

### The blocker

[lib/ai/providers.ts:1235](../../../lib/ai/providers.ts) runs exactly one non-streaming tool round per user turn, then streams the answer. The code already names this as a deliberate simplification with a known ceiling:

> `ponytail: exactly one tool round, because streaming a round means parsing …`

One round means the model cannot chain "look this value up" into "now act on it" within a single turn. Every workaround in the current tools exists because of this limit — the foreign-key name resolution inside `write-database.ts` exists purely to compress a lookup and a write into one call, and the previous design document calls this constraint out explicitly as the thing shaping it.

### Tier 2 — bounded multi-round tool loop

Replace the single round with a loop: run a tool round, feed the results back to the model, repeat until the model stops requesting tools or a step budget is exhausted, then stream the final answer. Default budget around five steps.

This is the highest-leverage change in the plan. With it, "add the w3engineers MCQ job, create the company if it does not exist, and move it to the MCQ column" resolves in a single turn without bespoke per-tool compression. Every further autonomy feature is policy layered on top of this loop rather than a new mechanism.

The step budget is also the blast-radius control: an agent that misbehaves is bounded by the loop, and the per-table allowlists and forced owner scoping continue to apply to every step within it.

### Tier 3 — scaffolding only

Persist each turn's tool records. These already reach the client: the pipeline surfaces `executedToolCalls`, the stream carries them as a `tool_calls` frame, and the chat page maps them onto the assistant message as `toolSteps` for the tool-chip UI. They are lost at persistence — `upsertSessionToDb` never stores the field, so the chips disappear on reload.

Storing the existing `toolSteps` field alongside the message therefore does two things at once: it restores tool chips on reloaded conversations, and it gives a per-step ledger, which is the prerequisite for undo, for replay, and for showing the user what an autonomous run actually did after the fact. No new field is introduced — the one already on the message is what gets stored.

Built now, not activated now. It is cheap to add while this area is open and expensive to reconstruct later, because the records cannot be recovered once the turn has ended.

Tier 3 itself — an agent carrying out several tasks across the application without per-step approval — is explicitly out of scope for implementation in this pass. Only the ledger is built.

## Out of scope

- Bulk or filter-based updates and deletes. Explicit ids only, as before.
- Board-position drag precision. Appending to the end of a column, as before.
- Schema tables not already opened up: `applications`, `interviews`, `positions`, `job_deadlines`, `smtp_config`, `extension_config`.
- A permission toggle separating read from write. They continue to share one switch.
- Server-side enforcement of the client-supplied permission array. The trust boundary is unchanged.
- Tier 3 execution policy, undo, and replay. Ledger only.

## Verification

The repository has no automated test runner, per `CLAUDE.md`. Verification is therefore:

- `npx tsc --noEmit` and `npm run lint`.
- One runnable check for the ordering fix: a save-then-load round trip asserting that a conversation of interleaved user and assistant messages returns in strict turn order, including the case where two messages share a timestamp. This is the smallest thing that fails if the ordering logic breaks.
- Manual smoke test, database access: with a fresh session and an existing one, ask the general assistant to create a job at a named company and place it in a named board column. Confirm the row appears on the board, and that an Applied-kind column also produces the application record.
- Manual smoke test, delete gate: ask the assistant to delete a scratch row and confirm it proposes first and only executes after a follow-up confirmation.
- Manual smoke test, ordering: reopen a conversation whose history is currently scrambled and confirm the turn order is repaired by the backfill.
