# Chatbot 2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Repair chat message ordering, give the chatbot working database write access in every chat, and lift the single-tool-round ceiling that blocks multi-step agent work.

**Architecture:** Message order becomes position-derived (`seq` column) instead of clock-derived. Database write access is unblocked by flipping one seed permission flag and backfilling it into existing sessions once. The streaming tool path gains a bounded multi-round loop, mirroring the loop the buffered path already implements. Each turn's tool calls are persisted as a ledger for future undo/replay.

**Tech Stack:** Next.js 16 App Router, React 19, TypeScript, `node:sqlite`, Tailwind CSS v4.

**Spec:** [docs/superpowers/specs/2026-08-16-chatbot-2.0-design.md](../specs/2026-08-16-chatbot-2.0-design.md)

## Global Constraints

- Schema changes require **both** `lib/db/schema.sql` (new databases) and `COLUMN_MIGRATIONS` in `lib/db/sqlite.ts` (existing databases).
- JSON and boolean SQLite columns must be registered in `lib/db/meta.ts`.
- User-owned reads and writes stay scoped by `user_id`.
- `jobs.status` is derived from `list_id`. Never write it directly.
- No test runner exists in this repo. Runnable checks are `scripts/verify-*.ts`, run with `node scripts/verify-<name>.ts`.
- Every change must pass `npx tsc --noEmit` and `npm run lint`.
- The audit trail never records field values — only action, resource, and row id.
- UX copy: sentence case, no exclamation marks, `Couldn't <verb> <noun>` for errors, product name is always `atTrack`.
- Branch: `feat/chatbot-2.0`.

### Task 1: Message ordering by position

**Files:**
- Modify: `lib/db/schema.sql` (chat_messages table, ~line 864)
- Modify: `lib/db/sqlite.ts` (`COLUMN_MIGRATIONS` ~line 273, `addMissingColumns` ~line 312)

- Modify: `lib/ai-chatbot/use-chat.ts:76-79`
- Test: `scripts/verify-chat-persistence.ts`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces: `chat_messages.seq INTEGER` column, populated for every row. Task 5 adds a second column to the same table and follows the same migration pattern.

**Background:** Assistant messages are created without `createdAt`. `upsertSessionToDb` fills the gap with `new Date().toISOString()` at save time, and because every save re-upserts every row, each assistant row is re-stamped to the newest save time on every turn. All user messages therefore sort ahead of all assistant messages. A timestamp-only fix is not enough — the user and assistant message objects are built in the same synchronous tick, so both would carry the same millisecond.

- [ ] **Step 5: Backfill `seq` for existing rows**

Existing rows have corrupted `created_at`, so the backfill derives order from SQLite's implicit `rowid` instead — messages were first inserted in array order, so `rowid` preserves the original turn order.

In `lib/db/sqlite.ts`, at the end of `addMissingColumns` (just before its `return`), add:

```ts
  // One-time repair of chat history written before `seq` existed. Ordered by
  // rowid, not created_at: assistant rows were re-stamped with the save time on
  // every upsert, so created_at no longer reflects turn order. Naturally
  // idempotent — once every row has a seq, this matches nothing.
  //
  // ponytail: correlated subquery, O(n^2) per session. Chat sessions hold tens
  // of messages, so this is milliseconds. Switch to a window function if a
  // session ever holds thousands.
  db.exec(`
    UPDATE chat_messages
    SET seq = (
      SELECT COUNT(*) FROM chat_messages AS m2
      WHERE m2.session_id = chat_messages.session_id
        AND m2.rowid <= chat_messages.rowid
    ) - 1
    WHERE seq IS NULL
  `);
```

- [ ] **Step 6: Write `seq` from message position**

In `lib/ai-chatbot/persistence.ts`, replace the message upsert loop (lines 40-51):

```ts
  // Upsert each message (idempotent by message id). `seq` is the array index,
  // not a timestamp: the two messages of a turn are constructed in the same
  // tick and would share a millisecond, and assistant rows get re-stamped on
  // every re-save. Position is the only tie-free ordering key here.
  for (const [index, m] of input.messages.entries()) {
    await client.from("chat_messages").upsert({
      id: m.id,
      session_id: s.id,
      user_id: userId,
      role: m.role,
      content: m.content,
      feedback: m.feedback ?? null,
      seq: index,
      created_at: m.createdAt ?? new Date().toISOString(),
    });
  }
```

`seq` is always taken from the server-side loop index and never from client-supplied data, so a stale client value cannot corrupt the order.

### Task 2: Unblock database access in every chat

**Files:**
- Modify: `lib/ai-chatbot/workspace.ts:180`
- Modify: `lib/ai-chatbot/prompt.ts:59`
- Modify: `lib/ai/tools/query-database.ts:30`
- Modify: `app/(dashboard)/ai-builder/chatbot/page.tsx:216-290`

**Interfaces:**
- Consumes: nothing from earlier tasks.
- Produces: `db_query` present in `enabledSourceIds` on the chat request, which is what makes `write_database` and `delete_database` visible to the model in Tasks 3-5.

**Background:** There are **three** compounding causes, and fixing only the first does not work. All three must land together, which is why they are one task.

1. **The source is seeded off.** `write_database` and `delete_database` are already implemented and registered in `TOOL_REGISTRY` and on the `general` agent. The `db_query` seed being `enabled: false` flows seed → `defaultEnabledIds` → session `connectedSourceIds` → request `enabledSources` → `isSourceAllowed`, which filters every tool carrying `sourceId: "db_query"` out of the declarations sent to the model.

2. **The system prompt tells the model to use a read-only path instead.** [lib/ai-chatbot/prompt.ts:59](../../../lib/ai-chatbot/prompt.ts) instructs:

   > "To query local database, provide a single read-only SQL code block (` ```sql SELECT... ``` `) and ask user to click 'Approve & Execute Query'."

   This is a real, separate database path: `components/ai-chatbot/markdown.tsx` renders any ` ```sql ` block with an Approve & Execute button wired to `executeLocalSqlQuery` ([lib/actions/database-query.ts](../../../lib/actions/database-query.ts)), which regex-blocks `INSERT|UPDATE|DELETE|...` and is therefore **incapable of writing** under any circumstances. Even with the tools unblocked, this instruction steers the model to emit SQL and demand a button click. It is the direct cause of the approval prompt the user is complaining about, and of the model's claim that it "can only execute read-only queries" — which was literally true of the path its own prompt told it to use.

3. **The read tool's description forbids writing.** [lib/ai/tools/query-database.ts:30](../../../lib/ai/tools/query-database.ts) ends with "Never ask for or expect write/delete access." That predates `write_database` and now actively teaches the model it has no write capability.

A fourth, downstream symptom: with no write tool, the model invented `SET stage = 'MCQ/Screening'`. There is no `stage` column — board placement is `list_id`, and `status` is derived from it. Routing through `write_database`'s `list` field removes the guesswork; the prompt change below also pins it explicitly.

```ts
// One-shot migration marker. Database Access changed from off-by-default to
// on-by-default; sessions saved before that carry a connectedSourceIds array
// without it. This runs once, then per-session toggles are authoritative —
// re-applying it on every load would undo a user who turned the source off.
const DB_ACCESS_BACKFILL_KEY = "attrack_db_access_backfill_v1";

function backfillDbAccess(stored: string[]): string[] {
  if (typeof window === "undefined") return stored;
  if (window.localStorage.getItem(DB_ACCESS_BACKFILL_KEY) === "done") return stored;
  return stored.includes("db_query") ? stored : [...stored, "db_query"];
}
```

```ts
/** Renders executed tool calls as prompt text. Shared by the intermediate
 *  rounds of the streaming tool loop and by its final follow-up prompt. Each
 *  result is capped: a whole-workspace dump inflates the prompt, and every
 *  extra input token is paid back as time-to-first-token. */
function renderToolContext(records: ToolCallRecord[]): string {
  return records
    .map((r) => {
      const body = r.result?.content ?? "";
      const clipped =
        body.length > MAX_TOOL_RESULT_CHARS
          ? `${body.slice(0, MAX_TOOL_RESULT_CHARS)}\n…[truncated, ${body.length - MAX_TOOL_RESULT_CHARS} more chars]`
          : body;
      return `### ${r.name}\n${clipped}`;
    })
    .join("\n\n");
}
```

```ts
  // Bounded multi-round loop. The buffered generateTextWithTools has done this
  // since it was written; the streaming path was capped at one round because
  // replaying vendor-native tool-result turns is fiddly. It does not have to —
  // results are folded in as prompt text below, and the round declares no
  // assistant turn to pair with, so plain text round-trips fine.
  //
  // The budget is the blast radius: a model that keeps calling tools stops
  // after MAX_TOOL_ROUNDS and answers with what it has.
  for (let roundIndex = 0; roundIndex < MAX_TOOL_ROUNDS; roundIndex++) {
    const roundPrompt =
      records.length === 0
        ? input.userPrompt
        : [
            input.userPrompt,
            "",
            "--- TOOL RESULTS SO FAR ---",
            renderToolContext(records),
            "--- END TOOL RESULTS ---",
            "Call another tool only if the question still cannot be answered. Otherwise call nothing.",
          ].join("\n");

    // Bounded separately from a full generation: this round returns a few dozen
    // tokens, so if it has not landed quickly the provider is not going to serve
    // tools usefully this turn.
    const round = await withTimeout(
      runRound(roundPrompt),
      TOOL_ROUND_TIMEOUT_MS,
      `${provider.name} tool round`
    );

    if (!round.functionCalls || round.functionCalls.length === 0) {
      // No tool wanted. On the first round there is nothing to ground the
      // answer in, so stream from the full grounded prompt — whatever text the
      // selection round produced was written against the lean prompt that told
      // it not to answer, so it is not usable. On a later round the model is
      // signalling it has enough, so fall through to the follow-up below.
      if (records.length === 0) {
        return { toolCalls: [], stream: await generateTextStream(chain, input, log) };
      }
      break;
    }

    for (const fc of round.functionCalls) {
      const record: ToolCallRecord = { name: fc.name, args: fc.args, status: "called" };
      onStep?.(record);
      try {
        const res = await executor(fc.name, fc.args, ctx);
        record.result = res;
        record.status = "done";
        if (res.citations.length) {
          (record as ToolCallRecord & { citations?: string[] }).citations = res.citations;
        }
      } catch (err) {
        record.status = "error";
        record.error = err instanceof Error ? err.message : String(err);
        record.result = { content: `Tool error: ${record.error}`, citations: [] };
      }
      records.push(record);
      onStep?.(record);
    }
  }
```
