--------------------------------------------------------------------------------
0. ONE-PARAGRAPH SUMMARY
--------------------------------------------------------------------------------
A single page at /ai-builder/chatbot renders an assistant-ui `Thread` driven by
an external-store runtime. Every turn POSTs the whole conversation to
/api/chat, which runs a hand-written 4-stage pipeline (context -> retrieval ->
agent/tool execution -> SSE stream) against the user's own configured AI
provider chain. Tools read and write the local SQLite database directly. Reads
and writes execute with no confirmation; DELETE is the only gated operation and
pauses the turn for an interactive Allow/Deny card. Chat history is durable in
SQLite with a localStorage mirror for instant paint.

Framework note: the pipeline is framework-free. There is no LangChain, no AI
SDK `streamText` in the chat path, no server-side agent framework. assistant-ui
is used for the *view layer only*, fed by a plain external store.

  app/api/chat/workspace/route.ts  GET. Read-only workspace snapshot: jobs

  app/api/chat/feedback/route.ts   POST/GET. Writes ai_feedback rows and
      chat_messages.feedback. NOTE: currently unreachable from the UI — see
      section 8.

2.2 The pipeline
  lib/ai-chatbot/pipeline.ts   (~759 lines) — the heart of the backend.

    executeChatPipeline(input) -> Response
      traceId minted here; requestStart/requestEnd events bracket the turn.
      Stage 1a buildChatContextBase  (pure, no I/O)
      Stage 1b resolveChainForModel  (DB + key decryption)   <-- these two
      Stage 2  retrieveChatContext   (local SQLite retrieval) <-- run in
                                                      Promise.all together
      Stage 3  executeAgent
      Stage 4  streamResponse

    Stage 1a — buildChatContextBase
      parses attachments to base64 images, resolves agent + persona, formats
      conversation history (MAX_HISTORY_TURNS=8, MAX_HISTORY_CHARS=6000,
      oldest dropped first), assembles the base system prompt, and classifies
      the auto-model rule.
      This stage does NO I/O, so it cannot see the user's providers. "auto"
      therefore resolves to a CAPABILITY (`autoRule`), not a model id; stage 1b
      turns that into a provider.
      Auto rules (only when model is "auto"/"Auto Hybrid Agent"/empty):
        images present                                    -> "images"
        prompt has ``` or code|function|typescript|react   -> "code"
        prompt has think|deep|math|algorithm               -> "reasoning"
        otherwise                                          -> "default"
      An explicit pick leaves autoRule undefined and targetModel = the picked
      id; the routeModel event reports rule "explicit".
      HISTORY: these rules used to resolve to hardcoded vendor ids
      (gemini-2.0-flash / claude-3-5-sonnet / deepseek-r1). On any workspace
      without those exact vendors configured, every auto turn fell through to
      chain[0] — one provider silently answered everything.

    selectProviderForModel(chain, targetModel, traceId, { owned, autoRule })
      (pure, exported for tests). `owned` is EVERY configured provider, not
      just the ones the "text" task route lists — the model picker is built
      from every provider, so the router has to be able to reach every one.
      autoRule turn:
        images    -> first provider in preference order that takes images
        reasoning -> first whose model reads as a reasoning model
        code      -> first anthropic provider
        default   -> no capability to match; the user's chain order stands
        preference order = the task-route chain first, then off-route
        providers. No capable provider -> chain unchanged.
      explicit turn:
        1. exact match on a chain provider's configured model  -> promote
        2. exact match on an OFF-ROUTE provider                -> adopt (head
           of the chain, route kept behind it as fallback)
        3. MODEL_CATALOG shorthand -> a provider of that vendor, chain first
           then owned, preferring one whose own model IS the catalog id.
           Never stamps a model id onto an openai_compatible row (live 400s).
        4. else leave the chain untouched.
      Capability tests live in lib/ai/model-capabilities.ts
      (modelSupportsImages, isReasoningModel) and are shared with the model
      picker in page.tsx so the badge and the router cannot drift.

    Stage 2 — retrieveChatContext
      classifyIntentAsync -> retrieveContext -> buildGroundedContext ->
      assembleGroundedSystemPrompt, then appends the agent's dynamic prompt if
      `agent.systemPrompt` is a function. Retrieval failure is swallowed and
      the turn continues ungrounded (logged).

    Stage 3 — executeAgent
      Filters the agent's tools through source permissions, builds JSON-Schema
      declarations, then decides `needsTools`:
        needsTools = toolDeclarations.length > 0
                     && !hasImages
                     && hasToolIntent
      hasToolIntent = intent !== "general_qa"
                      OR the prompt matches
                      /\b(search|find|query|lookup|fetch|show|list|get|check|
                        calculate|analyze|run|save|update|create|delete|sql)\b/i
      If true -> generateTextWithToolsStream. On throw, falls back to a plain
      generateTextStream (ungrounded-by-tools but still grounded by retrieval).

    Stage 4 — streamResponse
      Emits prelude frames (tool_calls, then each approval, then sources) and
      then pipes the provider token stream through. Errors mid-stream are
      emitted as an `{error}` frame rather than killing the connection.

2.3 Prompt assembly
  lib/ai-chatbot/prompt.ts        assembleChatSystemPrompt: persona
      instruction + markdown rule + optional web-search rules + conversation
      history + workspace context + the LOCAL DATABASE ACCESS block.
      The DB block tells the model to call query_database / write_database /
      delete_database directly, that reads and writes run immediately with no
      confirmation, that only delete pauses, and that the approval happens in
      the UI so it must never ask for confirmation itself or hand-write a SQL
      block asking the user to click something.
      That block's header is exported as LOCAL_DB_BLOCK_HEADER. The
      verification scripts import it rather than re-spelling the literal —
      they hardcoded "--- LOCAL SQLITE TABLES ---" and kept failing for three
      commits after the block was renamed, while the prompt itself was fine.
  lib/ai-chatbot/grounded-context.ts
      buildGroundedContext wraps each retrieved doc as
        [src:<citeRef>] <title>\n<text>\n[/src:<citeRef>]
      assembleGroundedSystemPrompt appends the ACCURACY RULES: facts inside
      [src] blocks are real and their IDs/names/dates/salaries/URLs/statuses
      must stay exact; anything outside is general knowledge and must be
      labelled as guidance; missing data must be admitted, never invented.

2.4 Intent classification
  lib/ai-chatbot/intent.ts
      Intents: job_list, job_detail, resume_review, outreach, interview_prep,
      crm_lookup, social_links, performance, general_qa.
      Tier 1: deterministic regex SIGNALS + persona hint boost. A
      GENERIC_CONCEPT match ("explain", "what is", "template"...) without an
      OWN_DATA_SIGNAL match suppresses retrieval, so "explain the STAR method"
      does not pull the workspace.
      Tier 2: optional injected LLM classifier (classifyIntentAsync). The
      pipeline currently calls it WITHOUT a classifier, so the effective
      methods are "heuristic" or "default".

      a table/column name and raw SQL), tableExists, getColumns,
      getColumnsWithTypes, getTextColumns, resolveOwnerColumn (user_id, then
      any *_user_id, else null), ALWAYS_BLOCKED_COLUMNS =
      {id, user_id, created_at, updated_at}.

  write_database invariants (lib/ai/tools/write-database.ts):
      - ownership is always forced to ctx.userId
      - id/created_at/updated_at are never model-writable
      - EXTRA_BLOCKED_COLUMNS blocks jobs.status — it is derived from list_id
        by a DB trigger; the model must move a job by setting list_id
      - TEXT primary keys get a crypto.randomUUID(); INTEGER PRIMARY KEY tables
        must NOT get an explicit id (they autoincrement)
      - moving a job into an Applied-kind list calls ensureApplication(), the
        same path drag-and-drop uses
      - dropped columns are reported back to the model as "(ignored: x, y)"
      - all raw SQL is wrapped in try/catch and returns a tool error string
      - every mutation logs column NAMES only via logResourceActivity

2.8 Delete approval flow (the only gated operation)
  lib/ai-chatbot/db-approval.ts       in-memory Map, 15-minute TTL.
      createPendingDbDelete -> approvalId
      consumePendingDbDelete — one-shot; validates user + expiry, deletes the
        entry before returning, so a decision cannot be replayed
      executeApprovedDelete — owner-scoped DELETE, one activity-log row per id
      Module-level and in-memory on purpose: a restart just clears it and the
      model re-proposes. Single local user.
  lib/ai-chatbot/db-approval-route.ts handleDbApprovalRequest — returns a
      one-frame SSE stream saying how many rows were deleted, or that the
      request expired, or that it was cancelled.

  Full sequence:
    1. model calls delete_database
    2. tool looks the rows up (owner-scoped), stores a pending entry, returns
       ToolResult.approval — NOTHING is deleted
    3. generateTextWithToolsStream sees record.result.approval and returns
       immediately (no further tool rounds — prevents re-proposal/chaining)
    4. pipeline emits `data: {"approval": {...}}`
    5. use-chat's onApproval fires -> page sets activeApproval
    6. DbDeleteApprovalCard renders Allow / Deny
    7. sendApproval POSTs the same conversation plus
       { dbApproval: { approvalId, decision } }
    8. /api/chat short-circuits to handleDbApprovalRequest before the pipeline

2.9 Provider layer
  lib/ai/providers.ts   (shared with the rest of the app, not chatbot-only)
    resolveProviderChain(userId, "text")  -> ResolvedProvider[] fallback chain
      Built from ai_task_routes.provider_ids for that task. A user can have
      providers configured that this route does not list — see
      resolveAllProviders.
    resolveAllProviders(userId)           -> every ai_providers row, decrypted,
      in creation order, regardless of task route. Backs both the no-route
      fallback inside resolveProviderChain and the chat router's off-route
      adoption.
    generateText / generateTextStream     plain completion, SSE-shaped output
    generateTextWithTools                 buffered multi-round tool loop
    generateTextWithToolsStream           THE ONE THE CHATBOT USES
    fetchUrlAsText                        backs the web_search tool

    generateTextWithToolsStream:
      - runs up to MAX_TOOL_ROUNDS (4) non-streaming tool-selection rounds
      - each round uses a deliberately tiny TOOL_SELECTION_PROMPT, not the
        heavy grounded prompt (input size dominates time-to-first-token)
      - prior results are folded into the next round's prompt as text under
        "--- TOOL RESULTS SO FAR ---" (no vendor-native tool-result replay
        needed, because these rounds declare no paired assistant turn)
      - per-result cap MAX_TOOL_RESULT_CHARS = 6000
      - round timeout TOOL_ROUND_TIMEOUT_MS = 30s (vs HOP_TIMEOUT_MS = 120s)
      - round 0 with no tool call -> stream the full grounded prompt directly
      - a pending approval short-circuits the loop
      - the final answer streams from a follow-up prompt containing
        "--- TOOL RESULTS ---"

    Per-vendor tool rounds:
      callGeminiToolRound             functionDeclarations / functionCalls
      callAnthropicToolRound          tools / tool_use blocks
      callOpenAICompatibleToolRound   tools[].function / message.tool_calls
        PLUS parseLongcatToolCallTags: LongCat-Flash writes its tool calls as
        a custom <longcat_tool_call> / <longcat_arg_key> / <longcat_arg_value>
        XML tag inside message.content instead of populating tool_calls. Their
        hosted API does not translate it, so without this parser the round
        returns "plain text" and the model narrates a success that never
        executed. Parsed into a synthetic OpenAI-shaped tool_calls array so the
        rest of the loop is unchanged.

2.10 Observability
  lib/log/ai-events.ts events emitted per turn, all joined by one traceId:
    requestStart, routeModel, routeProvider, intent, retrieval, routeTools,
    toolCall, requestEnd (+ per-provider-hop cost records via recordHop).
  routeModel  reports requestedModel, resolvedModel (null on an auto turn) and
    rule (images|code|reasoning|default|explicit).
  routeProvider reports autoRule, chainBefore/chainAfter (provider NAMES only)
    and reason: exact | adopted | vendor-catalog | auto-capability | unchanged.
    These two together are the answer to "why did THIS model serve the turn".
  Privacy: tool logging records argument NAMES and result SIZES only — never
  the values, which are the user's own job titles, contacts, and search text.

3. HOW FRONTEND AND BACKEND CONNECT
--------------------------------------------------------------------------------

3.1 Request body (POST /api/chat), built by page.tsx `buildBody` + use-chat
  {
    messages: [{ role, content, experimental_attachments }],
    model:            selectedModel.id            // "auto" or a real model id
    persona:          "general"                   // always general today
    personaPrompt:    workspaceAwarePrompt(...)   // persona + workspace tail
    workspaceContext: buildWorkspaceContextBlock(...)  // compact data block
    webSearchActive:  boolean
    enabledSources:   string[]                    // per-chat, else global
    sourceConfig:     { [sourceId]: {...} }       // de-obfuscated secrets
    dbApproval?:      { approvalId, decision }    // approval turns only
  }

3.2 Response: Server-Sent Events, text/event-stream
  data: {"tool_calls":[ToolCallRecord,...]}          // prelude, once
  data: {"approval":{approvalId,label,preview,sql}}  // prelude, per approval
  data: {"sources":["Job Applications", ...]}        // prelude, once
  data: {"choices":[{"delta":{"reasoning_content":"..."}}]}   // thinking
  data: {"choices":[{"delta":{"content":"..."}}]}            // answer tokens
  data: {"error":"..."}                              // mid-stream failure
  data: [DONE]

3.3 Client fan-out of those frames
  reasoning_content / reasoning / thinking -> message.thinking
  content                                   -> message.content
  sources[]  -> onSources  -> attaches to the latest assistant message
  tool_calls[] -> onToolSteps -> mapped to ToolExecutionStep[]
                 (status: called->running, error->failed, else completed)
  approval   -> onApproval -> page.activeApproval -> DbDeleteApprovalCard

3.4 ChatMessage -> assistant-ui parts (page.tsx `convertMessage`)
  order: reasoning -> tool-call(s) -> source(s) -> text
  Tool-call parts for query_database / write_database / delete_database (or
  any step with approvalRequired) additionally carry an assistant-ui
  `approval` + `interrupt` payload rendered by components/tool-fallback.tsx.
  CAVEAT: those inline buttons are decorative for the delete flow — the real
  delete gate is DbDeleteApprovalCard, which is driven by the separate
  `approval` SSE frame. See section 8.

3.5 Persistence path
  page.tsx effect on `messages` change
    -> writeCache(localStorage mirror)
    -> persistSession() PUT /api/chat/sessions
    -> upsertSessionToDb() -> chat_sessions + chat_messages upsert
  On load: readCache paints immediately, then fetchSessions replaces it.
  SQLite is the single authority; the mirror is never merged back. That
  asymmetry is deliberate — the old two-authority merge had no way to express
  "deleted", so deletes came back.

--------------------------------------------------------------------------------
4. WORKFLOWS
--------------------------------------------------------------------------------

4.1 Normal grounded turn
  user sends -> optimistic user+assistant rows -> POST /api/chat
  -> buildChatContextBase (agent, persona, history, model routing)
  -> Promise.all[ resolveChainForModel , retrieveChatContext ]
  -> executeAgent
       needsTools? -> generateTextWithToolsStream (up to 4 rounds)
       else        -> generateTextStream
  -> streamResponse (prelude frames, then tokens)
  -> client renders reasoning / tool chips / source chips / markdown
  -> effect persists the session to SQLite

4.2 Write turn (no confirmation, by design)
  "move X to MCQ" -> tool round 1 picks query_database (find list id) ->
  round 2 picks write_database with the resolved list_id -> executes ->
  final answer streams. jobs.status is recomputed by the DB trigger; moving
  into an Applied-kind list also creates the application row.

4.3 Delete turn (the only gated one)
  See 2.8. Two HTTP turns: propose, then decide.

4.4 Retrieval-only turn
  Intent classifies to a data intent but the prompt has no tool verb and the
  agent's tools are all source-blocked -> no tool round; the grounded
  system prompt alone carries the workspace facts.

4.5 Session lifecycle
  new chat -> in-memory + mirror only; earns a chat_sessions row on its first
  message. Title auto-generated from the first user message (6 words).
  delete/clear also removes vector chunks via deleteEntityChunks, but
  deliberately preserves ai_memories and vec_memories.

6. SOURCE PERMISSION MODEL
--------------------------------------------------------------------------------
  8 seeded sources (lib/ai-chatbot/workspace.ts deriveWorkspaceSources):
    jobs        Job Applications              on   -> search_jobs
    resume      Resumes & CVs                 on   -> get_resume
    contacts    Contacts CRM & Social Links   on   -> search_contacts
    memories    AI Memories                   on   -> search_memories
    ai_prompts  AI Prompts                    on   -> search_ai_prompts
    obsidian    Obsidian Vault                off  -> read_obsidian  (fs path)
    github      GitHub Repositories           off  -> search_github  (PAT)
    db_query    Database Access               on   -> query_database +
                                                      write_database +
                                                      delete_database
  Gating happens in THREE places and all three must agree:
    retrieval/index.ts  `allowed()`      — blocks the doc pull
    pipeline.ts         isSourceAllowed  — withholds the tool declaration
    tools/registry.ts   isSourceAllowed  — same check, registry-level
  Special case: contacts and links are merged both ways (granting one grants
  the other). web_search has no sourceId, so it is never gated.
  enabledSourceIds === undefined means "no permission model" (legacy client,
  no gating). `[]` means everything is off.
  Per-chat overrides live on chat_sessions.connected_source_ids; a chat with
  none falls back to the globally enabled set.

9. KNOWN SHARP EDGES
--------------------------------------------------------------------------------
  - Two approval UIs exist. The inline assistant-ui approval on tool-call parts
    (page.tsx convertMessage -> tool-fallback.tsx) is NOT wired to
    lib/ai-chatbot/db-approval.ts. The functional one is the banner card above
    the Thread. Do not "fix" one without deciding which survives.
  - Two different sets of providers are in play every turn: the model picker
    lists EVERY ai_providers row, while resolveProviderChain only returns the
    ones ai_task_routes names for "text". They are reconciled inside
    selectProviderForModel (rule 2, "adopted"). If that reconciliation is ever
    removed, picking an off-route model silently no-ops and chain[0] answers
    under the wrong model's name — the original symptom.
  - MODEL_CATALOG's shorthand ids (gemini-2.0-flash, claude-3-5-sonnet,
    deepseek-r1) are no longer produced by the auto-router. They survive only
    for older saved sessions whose chat_sessions.model holds one, and are still
    only meaningful if the user configured a provider of that vendor.
  - Settings > AI Providers is the ONLY source of chatbot models. The picker is
    rebuilt from listProviders() at mount and again on every window focus, so a
    provider added, removed, renamed, or repointed lands without a reload, and a
    selection whose row is gone is dropped back to "auto". Before that the list
    was fetched once per mount and AI_MODELS held a vendor catalog, so the
    dropdown could offer models the user had no key for.
  - A provider hop that streams to completion without enqueuing a single token
    falls through to the next chain entry (generateTextStream). That is
    deliberate — an empty answer is no answer — but it means the turn can be
    served by a provider the user did not pick while the UI still labels it with
    the picked one. It is recorded as an `ai.provider.hop` with ok:false and
    error "empty stream"; check for that line before believing the label. Seen
    live: an explicit Gemini pick finished ok with 17 output tokens and zero
    text parts, and the next chain entry answered under Gemini's name.
  - "auto" capability detection is a string heuristic over the model id the
    user typed (lib/ai/model-capabilities.ts). A provider row named something
    unrecognizable will not be picked for images or reasoning.
  - resolveProviderChain ignores ai_providers.verified_at. An unverified (or
    since-broken) provider still serves turns; only the no-provider lock screen
    checks `verified`.
  - `hasToolIntent` is a regex on the user's prompt. A write request phrased
    without any of those verbs will not get tools at all.
  - The tool-selection rounds see a lean prompt, NOT the grounded context. The
    model picks tools from the tool descriptions alone.
  - Source secrets (GitHub PAT, vault path) are base64-obfuscated in
    localStorage, not encrypted. Acceptable only because this is a local-first
    single-user app.
  - onToolSteps de-dupes by tool NAME in page.tsx, so two calls to the same
    tool in one turn collapse into one chip.
