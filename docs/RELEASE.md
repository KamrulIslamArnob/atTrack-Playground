# Release Checklist

This guide is the step-by-step checklist for shipping a new version of atTrack.

Use it when you want to:

- release a new web app build,
- release a new Windows desktop installer,
- publish an update that Electron auto-update can pick up,
- or make sure a code push becomes a properly versioned release.

## 1. Confirm what changed

Before you build anything, review the code that changed and decide whether the release is:

- web only,
- desktop only,
- or both.

If the change touches `electron/`, `scripts/`, packaging, update logic, or app startup, treat it as a desktop release too.

## 2. Update the version number

Bump the version in `package.json` for every release.

Use a new version number each time you ship so the installer name and auto-update metadata stay in sync.

## 3. Run the normal checks first

Run the project checks before building a release:

```bash
npm run lint
npm run build
```

If you changed database code, also run:

```bash
npx tsx lib/db/selfcheck.ts
```

## 4. Build the web application

For a browser or server deployment, build the Next.js app:

```bash
npm run build
```

Then start it in production mode if you need a quick verification pass:

```bash
npm run start
```

## 5. Build the desktop application

For the Windows desktop release, build the Electron package:

```bash
npm run electron:build:win
```

This runs the Next.js production build, prepares the standalone output, copies the files Electron needs, and generates installer/update artifacts in `release/`.

## 6. Verify the desktop app locally

Before you publish the installer, test the packaged-style app:

```bash
npm run electron:dev
```

Use this to confirm:

- the app starts from the standalone server,
- the main window loads,
- update checks still work,
- and your changed screens or workflows still open correctly.

## 7. Check the release artifacts

After `npm run electron:build:win`, inspect `release/` and confirm you have:

- the Windows installer,
- the update metadata files,
- and the expected version in the filenames.

Do not commit generated release artifacts unless your release process explicitly needs them in git.

## 8. Publish the release

Create a GitHub Release using the same version tag as `package.json`.

Upload the files from `release/` to that release so `electron-updater` can discover the new version.

The key files are the installer and the update metadata generated by Electron Builder.

## 9. Test the update path

After publishing, install the new desktop build and confirm that:

- the app opens normally,
- the update checker reports the current version correctly,
- and a future build would be able to detect the GitHub Release metadata.

If the app is already installed on a machine, use the built-in update checker from the desktop UI to confirm the packaged release is being read correctly.

## 10. Verify user data is safe

Desktop updates should not remove user data.

Check that the following still live in the user-data location, not inside the install folder:

- database files,
- uploaded documents,
- encrypted settings and keys.

If you change where data is stored, treat that as a migration task and test it separately before shipping.

## 11. Final release review

Before you call the release done, confirm all of these:

- the version number matches the GitHub Release tag,
- the desktop installer opens cleanly on Windows,
- the web build passes,
- the Electron app can start and check for updates,
- and the release artifacts in `release/` match the version you intended to ship.

## Suggested release order

For most updates, use this order:

1. Pull or merge the code you want to ship.
2. Bump `package.json` version.
3. Run checks.
4. Build the web app.
5. Build the Windows desktop app.
6. Test `electron:dev` locally.
7. Publish a GitHub Release with the `release/` artifacts.
8. Verify the installed desktop app can check for updates.
